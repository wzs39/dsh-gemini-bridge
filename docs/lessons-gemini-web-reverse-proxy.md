# 反代 Gemini 网页端：五个让「全部账号不可用」的坑

> 这是一份第一手复盘。所有结论都有实测数字，不是从协议文档推断来的。
>
> 目标场景：把 `gemini.google.com` 网页端包成 OpenAI 兼容的本地端点，三个 Pro 账号轮转，尽量别被 Google 封。
>
> 结果：三个账号全部能出字。但打通之前，**每一个坑都表现得像同一件事**——
> 「账号被风控了 / 会话过期了 / 额度用完了」。挨个排掉之后，五个原因彼此完全无关。

---

## 0. 先看结论：症状与真因的对应关系

这张表是整篇文章的价值所在。反代这类黑盒服务，**症状几乎不指向真因**。

| 你看到的现象 | 你以为的原因 | 真正的原因 | 章节 |
|---|---|---|---|
| 请求永远挂住，不返回也不报错 | 上游慢 / 网络问题 | CDP WebSocket 帧解析用数花括号切 JSON，响应里的字符串含成千上万个 `{` | [§1](#1-永远挂住cdp-帧解析用数括号是死路) |
| 三个账号全部「会话过期，请重新登录」 | cookie 失效 | CSRF token 的正则不接受冒号，所有健康 token 都匹配不上 | [§2](#2-健康的-token-被判成会话过期正则吃掉了冒号) |
| 请求不报错，但静默卡死 | 上游限流 | 请求参数 `bl` 取错了字段（取到纯数字，真实值是 `boq_...`） | [§3](#3-静默卡死参数取错字段比报错更难查) |
| 每个账号都返回 `empty answer`，但直连同一个账号正常 | 账号被降级 | 解析器多套了一层数组 + 把累积快照当增量拼接 | [§4](#4-解析器把完整响应丢掉了两个叠加的错误) |
| 一个账号额度用完，池里其他账号闲置却直接 429 | 额度真的没了 | 账号挑选只看「是否被 park」，不看各自的配额 | [§5](#5-三账号池退化成单账号配额账本没参与挑选) |
| 一次空回答，三个账号一起停 65 分钟 | 上游在限流 | 同一个请求里给「首次空回答」和「重试失败」各记一次异常分，凑满阈值 | [§6](#6-一次抖动停号一小时异常分被同一个请求刷满) |

**方法论上最要紧的一条**：这六个坑里有四个的**共同特征是「不报错」**。
黑盒反代里，「安静」永远优先怀疑自己这一侧的代码，而不是上游的态度。

## 1. 永远挂住：CDP 帧解析用数括号是死路

### 现象

`Runtime.evaluate` 调用永不 resolve。没有超时、没有异常、CPU 占用接近 0。

### 真因

当时用「拼接字节流 + 数 `{` 和 `}` 的平衡」来切分 WebSocket 消息：

```js
const i = this.#buf.indexOf('{', start)
// 数 { } 深度，深度回零就是一条完整消息
```

Gemini 的 `f.req` 响应是**嵌套转义 JSON**——外层 JSON 的字符串值里又装着完整的
JSON，里面有成千上万个不配对出现的花括号（在字符串内部）。深度计数必然错乱，
消息永远切不出来，pending promise 永不结算。

### 为什么这个 bug 特别阴险

同一个传输层，**换个 payload 形状就成败两分**：

- 抓 token 的响应 → 字符串值里没有花括号 → **能成功**
- 生成回答的响应 → 字符串值里全是花括号 → **必然挂死**

于是你会看到「登录正常、状态正常、就是生成不动」，非常容易被误判成上游限流。

### 修法

写一个真正的 RFC 6455 解析器。要点：

```js
// 帧头：FIN/opcode + MASK/len7
// len7 < 126  → 7 位长度
// len7 == 126 → 后 2 字节 16 位长度
// len7 == 127 → 后 8 字节 64 位长度
// opcode 0x0  → 续帧，拼到上一条消息
// opcode 0x9  → ping，必须回 0xA pong
// opcode 0x8  → close，结算所有 pending promise
```

客户端发出的帧**必须 mask**（4 字节掩码 + 逐字节异或）。

顺带修了写入端：原来 `>= 126` 字节一律走 16 位长度分支，
**超过 64KB 的 payload 头部会虚假声明长度**——发长 prompt 时会出问题。

### 教训

> **协议层不要走捷径。** 「用正则/数括号切 JSON」在 payload 是转义 JSON 时必炸。
> 而且它炸的方式是「安静地永不返回」，不是抛异常——这是最难查的一类失败。

## 2. 健康的 token 被判成「会话过期」：正则吃掉了冒号

### 现象

三个账号**同时**报"session expired; run `node bin/login.mjs`"。而浏览器里明明登录着。

### 真因

CSRF token（`SNlM0e`）的真实形状是：

```
AIza...很长的一串...:1793564141603
└──────── 22 字符 id ────────┘└─ 冒号 ─┘└ epoch 毫秒 ┘
```

正则写的是 `[\w\-_]+`。`:` 不在这个字符集里，所以**每个健康的 token 都匹配失败**。

### 为什么「三个账号同时」是个强信号

单账号失败 → 可能是这个号的 cookie 坏了。
**三个账号同时以同一种方式失败 → 几乎一定是代码问题**，不是账号问题。

这条判据在自查时非常有用：先问「这三个账号有什么共同点」，答案往往是「它们被同一段代码处理」。

### 修法

```js
// 错
const m = html.match(/SNlM0e":"([\w\-_]+)"/)
// 对：token 里可以有冒号
const m = html.match(/SNlM0e":"([^"]+)"/)
```

### 教训

> **正则的字符类是最容易写窄的地方。** 对不透明的 token，用 `[^"]+` 这种
> 「除了分隔符什么都接受」的写法，比枚举「合法字符」安全得多。

## 3. 静默卡死：参数取错字段比报错更难查

### 现象

请求不报错、不返回，纯粹挂住。

### 真因

发请求要带一个页面构建标识 `bl`。它从页面 HTML 里的 `FdrFJe` 字段取。
但 `FdrFJe` 在 HTML 里**出现多次**，第一个匹配是纯数字：

```
FdrFJe: -7730566936813324387     ← 正则第一次命中这个（错的）
```

真实值是 `WIZ_global_data` 里的：

```
boq_gemini-web-uiserver_20261029.22_p0
```

**发错值不会返回 4xx**，只会让服务端不返回内容——又是一个"安静失败"。

### 修法

优先从结构化的全局对象读，而不是从 HTML 里正则抓：

```js
// 权威来源：页面上的全局数据对象
window.WIZ_global_data.cfb2h   // 或 .FdrFJe
// HTML 正则只作兜底，且必须锚定形态前缀
/boq_[a-z0-9._-]+|prod-[a-z0-9._-]+/
```

### 教训

> **同一个字段名在 HTML 里出现多次时，第一次命中往往不是你要的那个。**
> 能读结构化对象就别读渲染后的 HTML；必须读 HTML 时，用「目标值的形态」锚定，
> 而不是用「字段名」。

## 4. 解析器把完整响应丢掉了：两个叠加的错误

### 现象

三个账号、每个账号单独直连都能出字（响应 22KB，答案就在里面），
但**走服务端一律** `upstream returned empty answer`。

这是最容易误判成「账号被降级」的一个坑——因为 `empty answer` 恰好是软封的经典信号。

### 真因（两个错误叠加，缺一不可）

**错误 A：多套了一层数组**

真实 payload 是：

```json
[["wrb.fr", null, "<inner-json-string>", ...], ["di", 5799]]
```

`wrb.fr` 条目是数组的**直接元素**。旧代码遍历两层，要求内层 `entry[0] === 'wrb.fr'`，
于是每次查找都 miss，函数必然返回 null。

合成测试的 fixture 也编码了**同样错误的**层级，所以 4 个单测全绿——测试跟着代码一起错。

**错误 B：把累积快照当增量拼接**

用 40 行的回答实测，每个 chunk 携带的是**累积快照**，不是增量：

```
块大小：2 → 20 → 44 → 68 → 92 → 117
每一块都是前一块的前缀延伸
```

- 旧代码「一找到文本就 return」→ 会在第一个片段就截断
- 直觉修法「拼接」→ 得到 `WEB-WEB-OKWEB-OKWEB-OK`
- **正确做法：取最后一块**

### 另外两个细节

文本实际落在 `inner[4][0][1]`，是**字符串片段数组**，要 join
（旧代码取 `inner[0][0]`）。

`<len>\n<json>` 的长度前缀实测**差一个字节**（声明长度把分隔符算进去了，
实际 body 里没有），导致后续每一帧都错位。所以现在：框切优先尝试，
但只有当它切出的合法 payload 数 ≥ 行切时才采信。

### 修法要点

```js
// 1. wrb.fr 是直接元素
for (const entry of payload) {
  if (entry[0] !== 'wrb.fr') continue
  ...
}

// 2. 累积快照 → 取最宽的那一块，而不是拼接
const text = snapshots[snapshots.length - 1].text

// 3. 文本是片段数组
const fragments = candidates[0][1]
const text = fragments.filter(f => typeof f === 'string').join('')
```

### 教训（这条最重要）

> **用合成 fixture 写的解析器测试，只能证明「解析器和 fixture 一致」，
> 不能证明它和真实上游一致。**
>
> 这两处错误在单测里全绿，因为 fixture 是照着错误的假设手写的。
> 唯一有效的做法：**把真实抓包存成 fixture**，让测试回放真实字节。

现在 `test/fixtures/` 里放着两份真实响应，`.gitattributes` 标记 `-text`
防止换行归一化改掉被断言的帧结构。

## 5. 三账号池退化成单账号：配额账本没参与挑选

### 现象

pro1 的窗口额度用完之后，下一个请求直接 429 失败，**而 pro2 / pro3 完全闲置**。

### 真因

账号挑选函数只检查「是否被 park」：

```js
pick() {
  for (...) {
    if (candidate.pausedUntil > now) continue   // 只看这一个条件
    return candidate
  }
}
```

配额是在后面的 `guard.admit()` 里才检查的——**那时账号已经选好了**，
于是拒绝直接终止调用，而不是去试下一个账号。

### 更深的坑：配置上的数字在骗人

```js
windowCap = ceil(requestsPerDay / budgetWindowsPerDay)
```

旧默认 `20 / 24` → `ceil(0.83) = 1`，即**每账号每小时 1 次**。
配置上写着「每天 20 次」，**日额度根本摸不到**。真人对话 20 秒一条，早就越界。

### 修法

1. 给 guard 加**只读**的可用性预检 `availability()`：冷却 / 日预算 / 窗口 /
   小时 / burst 休息 / 间隔，六道闸全部检查，**不消耗任何配额、不装定时器**。
2. `pick()` 跳过 `availability() === false` 的账号。
3. `nextUnpauseInMs()` 把配额阻塞也算进 retry-after。
4. 报错逐账号给原因，而不是一条泛泛的「全部 park」。

### 验收

修复后按顺序：请求 1 → pro2（pro1 窗口已满）→ 请求 2 → pro3 →
请求 3 → 诚实的 429，逐账号列出窗口用量和真实释放时间（188s）。

**流量真的转移了**，不是仅仅不再报错。

## 6. 一次抖动停号一小时：异常分被同一个请求刷满

### 现象

20 次压测，**0 成功**，三个账号同时被 park 65 分钟。

而直连同一个账号完全健康。

### 真因

```js
guard.anomaly('empty-answer', 2)         // 首次空回答
guard.anomaly('empty-answer-retry', 2)   // 重试又空
```

**两行都在同一个请求里执行**。阈值是 4，于是**一次瞬时抖动**就触发 1 小时冷却。
而且三个账号各吃一次，整池一起倒下。

### 修法

首次空回答**不记分**，只刷新 token 重试：
- 重试仍空 → 记 2 分（一次确认失败 = 两个信号中的一个）
- 第二次确认失败才触发冷却
- 触发后分数归零，避免一次失误反复续期
- 已经 park 的账号不重复 punish（不延长现有窗口）

### 验收

同一个 20 次压测：**0/20 → 16/20**。剩下 4 次是 pro1 窗口真的满了（17/17），
报错如实写 `window budget spent` 和释放时间，不再谎报异常。

### 教训

> **统计阈值的分母必须是「独立事件」，不是「相关事件」。**
> 重试失败是首次失败的**后果**，不是独立证据。把后果和原因一起计分，
> 等于把阈值砍半。

## 7. 关于「保守」：哪些参数能调，哪些不能

最初设为极低频（20 次/天），实测太保守。但**盲目调大是不安全的**，
因为参数互相咬合。最后做成档位：

| preset | windowCap | 日上限/账号 | 小时上限 | 间隔 | burst | 适用 |
|---|---|---|---|---|---|---|
| `cautious` | 2/h | 48 | 6 | 15–45s | 20min/8min | 新号首周 |
| `balanced` | 5/h | 120 | 12 | 6–18s | 30min/5min | 正常重度自用 |
| `brisk` | 17/h | 408 | 30 | 2–6s | 40min/3min | 长 agent 跑批 |

**关键判断：哪些闸门在保护账号**

护号的是这三道，**任何档位都不松**：

1. **请求间隔**（`minGapMs`–`maxGapMs`）——越像真人越好，这是最重要的一道
2. **小时上限 + burst 强制休息**——打断「连续机器节奏」
3. **异常检测**——空回答是降级第一信号

**调档只放宽日/窗口额度**，这三个不动。失败反应
（`failureBreakerAt`、`anomalyThreshold`）在三个档位**逐字节相同**，有测试断言。

> **调吞吐是调优选择，「多久判定账号出事」不是。**
> 这两类参数必须能分开调，否则一旦提高吞吐就会顺带削弱事故反应。
> 这也是为什么值得把 15 个散装数字收成档位——手调一个会悄悄弄坏另一个。

## 8. 顺手挖到的两个配置层 bug

### 8.1 `null` 被当成「没有意见」

`mergeDeep(DEFAULTS, overrides)` 里，`null` 值被跳过，导致 DEFAULTS 里的
`null` 占位符**遮蔽**了用户配置的值。

修法：把 `null` 当作显式的「取消此字段」，让它穿透合并。

### 8.2 浅拷贝把改动写回了模块级默认值

```js
return { ...base }   // 浅拷贝
```

调用方（`applyPacingPreset`）修改合并结果时，**改动直接落到模块级 `DEFAULTS`**。
于是**第一次 `loadConfig()` 把自己的 preset 永久烘焙进去**，之后同进程内所有加载
都忽略自己的配置。

只在 `loadConfig()` 被调用两次时复现——而这**正是测试套件和热重载宿主的行为**。
单独跑一次永远看不到。

修法：`return structuredClone(result)`。

### 教训

> **共享可变默认值是个定时炸弹。** 配置加载函数必须返回调用方可以随便改的副本。
> 更阴的是：这种 bug 只在「加载两次」时出现，而手工验证通常只加载一次。

## 9. 怎么查这类问题（可复用的排查顺序）

黑盒反代出问题时，**按这个顺序排，不要从上游开始怀疑**：

1. **先绕开服务端，直连底层**
   —— 写个脚本直接调 `generateRaw`，看上游到底给没给内容。
   这一步能立刻分离「上游问题」和「我这侧问题」。
   本次五个坑里有四个都是「上游其实健康」。

2. **多账号同时以同样方式失败 → 代码问题**
   —— 单账号失败可能是账号；三个账号同时同症状，几乎一定是同一段代码。

3. **把真实响应存成 fixture**
   —— 合成 fixture 只能证明「代码和我的假设一致」。

4. **区分「安静失败」和「明确拒绝」**
   —— 没有 4xx、没有异常、就是不动：优先查传输层、参数、解析器。
   有明确的 429/403：才去查配额和风控。

5. **验证修复要看「行为是否真的变了」，不是「错误是否消失」**
   —— 配额修复的验收标准是「请求真的落到 pro2」，不是「不再 429」。

6. **压测要看统计，不要看单次**
   —— 单次成功说明不了吞吐；20 次连续才暴露异常分被刷满的问题。

## 11. 一句话总结

> 这六个坑全部表现为「账号好像被风控了」，**没有一个真的和风控有关**。
> 反代 Gemini 网页端，绝大部分「封号预兆」其实是自己代码在安静地失败。
>
> 排查铁律：**先证明上游健康，再怀疑上游。**
